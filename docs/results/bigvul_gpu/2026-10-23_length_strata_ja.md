# BigVul（GPU）の途中結果と長さ別の確認（2026-10-23）

GPU 機（RTX 3090）の run を利用者が貼った出力から記録する。各腕 3 seed、test 18,124 関数（脆弱 950）。
hybrid（辺あり）は実行中で、ここには入っていない。

## test F1 と ROC-AUC

| 腕 | F1（検証で調整した閾値） | ROC-AUC |
|---|---|---|
| codebert | 0.427 ± 0.018（0.4056 / 0.4377 / 0.4364） | 0.831 ± 0.004 |
| hybrid（辺をシャッフル） | 0.443 ± 0.004（0.4472 / 0.4388 / 0.4415） | 0.815 ± 0.026 |
| graph_only | 0.304 ± 0.013（0.2897 / 0.3154 / 0.3059） | 0.773 ± 0.004 |

`compare_runs.py --seed_bootstrap`（二段 bootstrap）で、hybrid（辺をシャッフル）と codebert を比べた。

- F1 の差は +0.016 [−0.007, +0.040]（P(A>B) 0.90）。
- ROC-AUC の差は −0.016 [−0.041, +0.011]（P(A>B) 0.13）。

どちらも 0 と区別できず、向きも逆。辺を壊したグラフ枝がテキストに何かを足している証拠はない。

## 読み方

- **見えない欠陥の方が高く当たっている。** codebert は、修正箇所が窓の外にあって読めていない関数（hidden）を、窓の中にある関数（visible）より高く順位づけている。
- **効いているのは長さ。** hidden の関数は長く、長さだけで非脆弱と見分けられる（AUC 0.871）。visible では長さは役に立たない（0.448）。モデルは欠陥そのものではなく、長さ（とそれに伴う特徴）で当てている。
- **BigVul では、窓の外を読む構造の利点は示せない。** 関数単位のラベルが長さで当たってしまうので、窓の外を読んでも点に表れない。Risse et al.（ISSTA 2025, "Top Score on the Wrong Exam"）の指摘と同じ形。
- **グラフ枝も関数の末尾を見ていない。** `--max_nodes 500` は（行、列）順の先頭 500 ノードを残す。長い関数では、グラフ枝も末尾を落としている。graph_only の hidden と visible の差（−0.161）は、テキスト以上に長さに頼っていることを示す。
- **確かめるには、長さで当てられない試験が要る。** 脆弱な版と修正後の版の対（func_before / func_after）なら長さはほぼ同じで、違いは修正箇所だけになる。修正箇所が窓の外にある対では、窓 510 のテキストモデルには 2 つの入力が同一に見える。そのため、構造上見分けられない。
