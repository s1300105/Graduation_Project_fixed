# Structure-aware code language models (2020–2026): catalogue, scale, and data-efficiency evidence

Scope note: notes compiled 2026-11-02 from primary sources (arXiv/ACL/PMLR/ACM pages) where possible. Items marked **[unverified]** could not be confirmed from a primary page in this pass. Vulnerability datasets (Devign, BigVul, …) are treated as unreliable benchmarks; see label-quality section under Key Question 1 (item V).

## Key Question 1 — Catalogue: verified details of the canonical structure-aware code LMs (2020–2024) plus 2024–2026 additions

### Takeaway
The canonical line (GREAT → GraphCodeBERT → Code Transformer / TPTrans / AST-Trans → TreeBERT / SynCoBERT / UniXcoder / StructCoder → AST-T5) injects structure either into attention (masks or score biases), into the input as extra positions/serialized trees, or only into the pretraining objective; nearly all are ≤ 250M-parameter encoders or encoder-decoders pretrained or continually pretrained from scratch, with gains typically of 0.5–3 points on CodeXGLUE-style tasks and larger gains on low-resource/code-to-code settings. 2024–2026 work shifts to (a) objective-only structure (AST-T5, AST-FIM, GrammarCoder) and (b) GNN/graph-encoder branches bolted onto frozen or LoRA-tuned decoder LLMs (GALLa, CGBridge, IRCoder, CodeGRAG, CGFuse, PRISM, CGM).

### Cited Findings

**A. 2020–2022 foundational models**

- **GREAT — "Global Relational Models of Source Code"** (Hellendoorn, Maniatis, Singh, Sutton, Bieber; ICLR 2020). Structure: program graph edges (data flow, control flow, etc.) from the authors' own analysis pipeline (public dataset is a synthetic variable-misuse set derived from ETH Py150 Open; original graph data not released for licensing reasons). Where structure enters: GREAT = "Graph Relational Embedding Attention Transformer", which adds graph edge-type information to Transformer attention (a relative-attention bias keyed on edge type); "Graph Sandwich" models interleave GNN message passing with Transformer layers. Task: variable-misuse localisation & repair. Findings: a graph baseline beat prior SOTA by ~20%; hybrids added a further 10–15% while training faster with fewer parameters. Author list differs between the Google page and the ICLR poster page; the PDF order (Hellendoorn, Maniatis, Singh, Sutton, Bieber) is authoritative. — [Google Research page](https://research.google/pubs/global-relational-models-of-source-code/); [ICLR 2020 poster page](https://iclr.cc/virtual/2020/poster/1945); [dataset/code repo listing](https://awesome.ecosyste.ms/projects/github.com%2Fgoogle-research-datasets%2Fgreat)
- **GraphCodeBERT** (Guo et al.; ICLR 2021). Structure: data-flow graph (DFG; "where-the-value-comes-from" edges between variables) obtained by parsing code to an AST with tree-sitter, taking variables as AST leaves and adding edges from source variable to the variable whose value it determines. Where structure enters: DFG nodes are appended to the input sequence and a **graph-guided masked attention** restricts attention according to DFG edges and variable–token alignment; two structure-aware pretraining tasks (edge prediction, node alignment) plus MLM. Model: 12-layer, 768-hidden, 12-head Transformer initialised from CodeBERT (≈125M; parameter count not stated on page). Pretraining: CodeSearchNet, ≈2.3M functions, 6 languages, 200K steps (~83 h). Results vs CodeBERT: code search MRR 0.713 vs 0.693 (filtered), BigCloneBench F1 0.950 vs 0.941, Java→C# BLEU/Acc 80.58/59.4 vs 79.92/59.0, C#→Java 72.64/58.8 vs 72.14/58.8, refinement small BLEU/Acc 80.02/17.3 vs 77.42/16.4. Ablation (code search MRR): full 0.713; w/o edge prediction 0.707; w/o node alignment 0.703; w/o data flow 0.693. — [arXiv abs](https://arxiv.org/abs/2009.08366); [ar5iv full text](https://ar5iv.labs.arxiv.org/html/2009.08366)
- **Code Transformer — "Language-Agnostic Representation Learning of Source Code from Structure and Context"** (Zügner, Kirschstein, Catasta, Leskovec, Günnemann; ICLR 2021, TUM/Stanford). Structure: AST; model uses only language-agnostic features computable from the AST (the abstract page does not spell out the mechanism; the paper's attention over multiple AST-derived relative distances is **not re-verified** in this pass). Tasks: code summarisation (method naming) in five languages; first multilingual code summarisation model; "multilingual training only from Context does not lead to the same improvements" as Structure+Context; strongest multilingual gains on low-resource languages. Code: github.com/danielzuegner/code-transformer. — [arXiv abs](https://arxiv.org/abs/2103.11318); [ICLR slides](https://www.cs.cit.tum.de/fileadmin/w00cfj/daml/code-transformer/iclr_2021_slides.pdf)
- **TPTrans — "Integrating Tree Path in Transformer for Code Representation"** (Han Peng, Ge Li, et al.; NeurIPS 2021). Structure: AST paths; relative (token-to-token pairwise) paths and absolute (leaf-to-root) paths encoded by bidirectional GRUs **replace relative and absolute position embeddings in self-attention** (relative path encoding acts as relative relation bias). Task: code summarisation in four languages. Exact numbers not extracted. — [NeurIPS proceedings PDF](https://papers.nips.cc/paper_files/paper/2021/file/4e0223a87610176ef0d24ef6d2dcde3a-Paper.pdf); [NeurIPS poster page](https://neurips.cc/virtual/2021/poster/26141)
- **AST-Trans — "Code Summarization with Efficient Tree-Structured Attention"** (Ze Tang et al.; ICSE 2022; preprint titled "AST-Transformer"). Structure: AST; two relationship matrices — ancestor–descendant (shortest-path distance in AST) and sibling (horizontal distance) — with infinity for non-related pairs, used to **mask/weight attention** (relative-position-style tree attention), outputs of the two attentions concatenated and projected. Claims significant gains over SOTA and several-times efficiency over standard Transformers on two summarisation datasets (speed-up figure truncated in source). Code: github.com/zetang94/ICSE2022_AST_Trans. — [arXiv preprint](https://arxiv.org/pdf/2112.01184); [ICSE 2022 page](https://conf.researchr.org/details/icse-2022/icse-2022-papers/160/AST-Trans-Code-Summarization-with-Efficient-Tree-Structured-Attention)
- **TreeBERT** (Xue Jiang, Zhuoran Zheng, Chen Lyu, Liang Li, Lei Lyu; UAI 2021, PMLR 161:54–63). Structure: AST fed to the model (tree-based MLM + node-order prediction objectives); generation tasks; transfers to an unseen language. — [PMLR page](https://proceedings.mlr.press/v161/jiang21a.html); [arXiv](https://arxiv.org/abs/2105.12485v2)
- **SynCoBERT** (Xin Wang, Yasheng Wang, Fei Mi, Pingyi Zhou, Yao Wan, et al.; arXiv Aug–Sep 2021, Wuhan Univ./Huawei Noah's Ark; **no peer-reviewed venue confirmed** — the UAI attribution sometimes seen is not supported by the sources found). Structure: tree-sitter AST serialised by DFS as an extra input modality; objectives: Identifier Prediction, AST Edge Prediction, multi-modal contrastive learning across code/comment/AST. Reported POJ-104 MAP@R (as tabulated by UniXcoder): 88.24. — [arXiv abs](https://arxiv.org/abs/2108.04556); POJ-104 figure from [UniXcoder ar5iv](https://ar5iv.labs.arxiv.org/html/2203.03850)
- **UniXcoder** (Guo, Lu, Duan, Wang, Zhou, Yin; ACL 2022). Structure: AST flattened by a one-to-one mapping (`<node,left> children <node,right>`) used **only in pretraining**; at fine-tuning/inference only code leaves are kept because explicit AST adds parsing time and ~70% input length (non-terminals dropped with p=0.5 in pretraining to narrow the gap). Mask-attention matrices with prefix adapters control encoder/decoder modes; contrastive + cross-modal generation objectives. Model: 12 layers, 768 hidden. POJ-104 MAP@R: UniXcoder 90.52, CodeT5-base 88.65, SynCoBERT 88.24, PLBART 86.27, GraphCodeBERT 85.16, CodeBERT 82.67. BigCloneBench F1: UniXcoder 95.2, CodeT5 95.0, GraphCodeBERT 95.0, CodeBERT 94.1, PLBART 93.6. Ablation "w/o AST": POJ-104 88.74 (full 90.52); CSN MRR 74.2 (74.4); summarisation BLEU-4 19.33 (19.30 — i.e., AST did not help); generation EM 22.60 (22.60); zero-shot code-to-code search MAP 17.06 (20.45). — [arXiv abs](https://arxiv.org/abs/2203.03850); [ar5iv full text](https://ar5iv.labs.arxiv.org/html/2203.03850)
- **StructCoder** (Tipirneni, Zhu, Reddy; ACM TKDD, DOI 10.1145/3636430; arXiv 2022). Structure: tree-sitter AST + DFG (CodeXGLUE/CodeBLEU DFG extractor). Where structure enters: AST leaves and DFG variables are appended as extra encoder positions; leaf embeddings = Σ over root-to-leaf path of (node-type emb ⊙ height emb); **structure-aware self-attention** adds structure terms (leaf–leaf: log count of shared root-path nodes; variable–variable kept only where DFG edge exists; code–leaf/code–variable only where linked); decoder has auxiliary AST-path prediction and data-flow prediction heads (loss weight 0.1, nothing extra generated at inference). Model: 224M (extends CodeT5-base 223M). CodeXGLUE Java→C# BLEU/EM/CodeBLEU 84.43/66.90/88.19 vs CodeT5 83.88/64.70/87.38; C#→Java 80.43/68.70/85.98 vs 79.71/67.50/85.51; CONCODE 41.35/22.40/44.44 vs 40.73/22.30/43.20; APPS intro strict acc 2.5 vs 1.70. Ablation (small T5, val CodeBLEU Java→C#/C#→Java): no structure 68.09/62.45; DFG-enc 68.07/63.11; DFG-dec 68.96/63.13; AST-enc 68.96/63.57; AST-dec 69.39/63.57; all 69.56/64.26; all + structure-based DAE pretraining 84.50/82.67. **Negative:** DFG in encoder slightly lowers Java→C# (BLEU 59.20 vs 60.00); DFG contributes less than AST; summarisation gains only on Go (24.18 vs 19.56), behind CodeT5 on PHP (25.16 vs 26.03); AST+DFG inputs raise inference time ~28–29% and input length 75–83%. — [arXiv html v3](https://arxiv.org/html/2206.05239v3); [VTechWorks record](https://vtechworks.lib.vt.edu/items/ad9630c4-374f-4400-a89b-fb1bd768edae/full)
- **CodeSage ("Code Representation Learning at Scale", 130M/356M/1.3B encoders, ICLR 2024)** is **not** an AST-injection model: structure awareness comes from a deobfuscation (DOBF) + MLM objective that the authors argue "implicitly encodes data flow and AST". Included only to flag the naming confusion with "CodeSAGE"; no AST input or attention change. — [project page](https://code-representation-learning.github.io); [HF card](https://huggingface.co/codesage/codesage-base)

**B. 2024 structure-in-objective / structure-as-text work**

- **AST-T5** (Linyuan Gong, Mostafa Elhoushi, Alvin Cheung; ICML 2024, PMLR 235:15839–15853). Structure: tree-sitter AST, no program analysis, no architecture change. Where: pretraining only — AST-aware segmentation (DP to keep subtrees intact in 1024-token windows) and AST-aware subtree span corruption (25% mask). Model: 226M T5-Base-like. Data: ~408 GB code (GitHub BigQuery) + Wikipedia/OpenWebText; 524B tokens. Results: HumanEval pass@1 12.8 (CodeT5+ base 12.0); Bugs2Fix EM 23.8/16.1 vs CodeT5 21.6/14.0; Java↔C# EM 68.9/72.3 vs 65.9/66.9; clone F1 98.6 vs 97.2; defect acc 65.8 (= CodeT5); Concode EM 22.9 vs 22.3. Ablation (avg): T5 baseline 44.2 → +AST-aware segmentation 45.7 → +subtree corruption 47.0 → +25% mask 47.7; 50% mask 46.2 (hurts transpilation/understanding). No scaling or data-efficiency study. — [PMLR](https://proceedings.mlr.press/v235/gong24c.html); [arXiv html](https://arxiv.org/html/2401.03003v1)
- **"Structured Code Representations Enable Data-Efficient Adaptation of Code Language Models"** — verified authors: **Mayank Agarwal, Yikang Shen, Bailin Wang, Yoon Kim, Jie Chen** (MIT-IBM Watson AI Lab / IBM Research / MIT); **arXiv:2401.10716, 19 Jan 2024; no peer-reviewed venue listed on arXiv.** Structure: concrete syntax trees (CSTs; footnote points to tree-sitter) serialised by hybrid pre/post-order traversal with opening/closing non-terminal markers added as single tokens to the tokenizer; **no architecture change**. Models: CodeT5 (60M/220M/770M) and CodeGen-Multi 350M (decoder-only). Continual pretraining on ~8.45M samples (CodeSearchNet + Stack C/C#), 1 epoch (≈15 h on 32 V100 for CodeT5), with objectives MSP/MNP/tree↔text. Full details on low-resource curves in Key Question 3. — [arXiv abs](https://arxiv.org/abs/2401.10716v1); [arXiv html](https://arxiv.org/html/2401.10716v1)
- **SAT — "Structure-aware Fine-tuning for Code Pre-trained Models"** (Jiayi Wu, Renyu Zhu, Nuo Chen, Qiushi Sun, Xiang Li, Ming Gao; arXiv 2404.07471, Apr 2024; ECNU/NetEase/NUS; venue not confirmed). Structure: tree-sitter AST → leaf-to-leaf shortest-path distance matrix. Where: **auxiliary loss** (Sinkhorn divergence between first-layer attention matrix and a learnably scaled distance matrix), L = L_task + α·L_struct; no architecture change. Models: RoBERTa, CodeBERT, GraphCodeBERT, CodeT5 (sizes not stated). Tasks: CSN summarisation (5 langs), CodeXGLUE Java↔C#. Largest gain RoBERTa 71.99→76.67 overall BLEU; CodeT5 gains least (attributed to identifier-aware pretraining). Low-resource table in Key Question 3. Not applicable to text-to-code. — [arXiv html](https://arxiv.org/html/2404.07471)

**D. 2025–2026 structure-in-objective / structure-as-tokens for decoder LLMs**
- **AST-FIM — "Structure-Aware Fill-in-the-Middle Pretraining for Code"** (Linyuan Gong, Alvin Cheung, Mostafa Elhoushi, Sida Wang; UC Berkeley/FAIR; arXiv 2506.00204, May 2025). AST-guided masking (single-node + aligned-span) for FIM pretraining of 1B and 8B decoder models; up to +5 points over random-character FIM on FIM benchmarks, largest on real-world edits (new Real-FIM-Eval from 30K+ commits, 12 languages). Notes that Qwen2.5-Coder already uses AST-guided FIM in post-training. — [arXiv abs](https://arxiv.org/abs/2506.00204v1)
- **GrammarCoder — "Grammar-Based Code Representation: Is It a Worthy Pursuit for LLMs?"** (Qingyuan Liang, …, Yingfei Xiong; PKU et al.; arXiv 2503.05507v2, rev. Dec 2025). Grammar rules from AST preorder mixed with BPE tokens in one vocabulary; continued pretraining (~10B Python tokens) of DeepSeek-Coder-1.3B, Qwen2.5-1.5B, Qwen2.5-7B. Vs token-based continued pretraining on same data: HumanEval 63.4 vs 43.9 (1.3B), 65.9 vs 50.6 (1.5B), 76.8 vs 68.9 (7B); MBPP 68.3 vs 61.4, 64.8 vs 60.3, 85.2 vs 81.5. Gains persist at 1.3B–7B but no larger scales tested; token baselines already make almost no syntax errors; parsing fails on incomplete code; table inconsistencies noted. — [arXiv html v2](https://arxiv.org/html/2503.05507v2)
- **Gong dissertation (UC Berkeley EECS-2025-50, May 2025)**: SAFIM benchmark (15 LLMs) "challenge[s] the idea that 'big model = good performance'", arguing pretraining strategy and data quality matter more; AST-T5 and AST-FIM chapters. — [EECS tech report PDF](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2025/Archive/EECS-2025-50.pdf)
- **TreeDiff** (arXiv 2508.01473, 2025): AST-node-level masking for diffusion code LLMs — snippet-level only. — [arXiv](https://arxiv.org/pdf/2508.01473)
- **cAST** (Findings of EMNLP 2025): AST-based structural chunking for code RAG; +4.3 Recall@5 on RepoEval retrieval, +2.67 pass@1 — structure in the retrieval pipeline, not in the LM. — [ACL Anthology PDF](https://aclanthology.org/2025.findings-emnlp.430.pdf)

**V. Vulnerability-dataset label quality (why Devign/BigVul numbers are discounted here)**
- Croft et al. (ICSE 2023) manually checked labels: accuracy 0.80 (Devign), 0.543 (Big-Vul), 0.286 (D2A); 20–71% of vulnerability labels inaccurate. — [arXiv](https://arxiv.org/abs/2301.05456v1)
- "Top Score on the Wrong Exam" (arXiv 2408.12986) re-measured Devign vulnerable-labelled functions under a stricter standard: ≈47% accurate. — [arXiv](https://arxiv.org/pdf/2408.12986)
- PrimeVul (Ding et al., ICSE 2025): a 7B model scores 68.26 F1 on BigVul but 3.09 F1 on PrimeVul; prior benchmarks "significantly overestimated" performance due to automatic labelling noise, duplicates, and leakage. — [arXiv](https://arxiv.org/html/2403.18624v2)
- Vul-LMGNNs (Joern CPG + GGNN with CodeBERT/GraphCodeBERT/CodeT5 node init, prediction interpolation λ=0.8) reports Devign F1 63.82, ReVeal F1 53.09, DiverseVul F1 32.59; the paper notes Devign labels come from commit messages/diffs but does not analyse noise. — [arXiv html v2](https://arxiv.org/html/2404.14719v2)
- K-ASTRO v3 uses BigVul/DiverseVul/PrimeVul with OpenAI embeddings (ada-002, 3-small) frozen + a 1M-parameter structure-aware Transformer block whose attention map is biased by AST node-type co-occurrence matrices; PrimeVul (4 CWEs) F1 92.33; but no fine-tuned-LLM baseline numbers are given. — [arXiv html](https://arxiv.org/html/2208.08067)

### Inferences
- Across the 2021–2022 generation, the marginal gain from explicit structure over a strong text-only pretrained baseline of the same size is small on standard full-data benchmarks (GraphCodeBERT +0.9 F1 BigCloneBench, +2.0 MRR; StructCoder +0.5–1 BLEU; UniXcoder's AST ablation ±0–2 points and zero effect on summarisation/generation) but larger on structure-sensitive tasks (zero-shot code-to-code search −3.4 MAP without AST; variable misuse in GREAT).
- The most consistent positive signal comes from pretraining objectives aligned with structure (AST-T5, AST-FIM, GrammarCoder, UniXcoder) rather than from runtime structural inputs, which add 70–83% sequence length and ~28% inference time (UniXcoder, StructCoder).

### Gaps
- Code Transformer's exact attention mechanism and numbers, TPTrans numbers, and AST-Trans speed-up factor were not re-extracted from full texts.
- No peer-reviewed venue could be confirmed for Agarwal et al. 2024, SAT 2024, SynCoBERT, Vul-LMGNNs, or CGM.
- Semantic Scholar citation API returned HTTP 429 for GraphCodeBERT/Agarwal/GALLa citation graphs, so the 2025–2026 citing-paper sweep was done via web search instead and is not exhaustive.

## Key Question 2 — Does explicit AST/data-flow structure still help large code LLMs (StarCoder, CodeLlama, Qwen2.5-Coder, DeepSeek-Coder scale), and what do probing studies say?

### Takeaway
No paper found runs a clean "structure vs. no structure" comparison at ≥30B; at 1B–14B the evidence is mixed-positive: GALLa reports +2% to +36% relative average gains across seven LLMs (350M–14B) with no clean decline in gain with scale, CGBridge and IRCoder report gains on frozen 1.3B–7B models, and GrammarCoder gains persist to 7B; but Su & McMillan (2025) find static-analysis pretraining does not reliably improve downstream tasks on CodeLlama-13B, and probing work (Anand et al. 2024; Ma et al. TOSEM 2024) finds that larger/fine-tuned models encode syntax and data flow *worse* or no better than 125M–220M encoders.

### Cited Findings

**Positive / mixed evidence at LLM scale**
- GALLa (ACL 2025): GNN (DUPLEX, ~7M params) over AST+DFG extracted with JetBrains PSI from 240K Python + 75K Java CodeNet programs (626K graph pairs); graph tokens prepended via a cross-attention adapter; stage 1 LLM frozen, stage 2 LLM unfrozen (LoRA r=64 for the 7B–14B models); **graph encoder discarded at inference** so no runtime cost. Average over 5 CodeXGLUE/CodefuseEval tasks, baseline → GALLa: CodeGen-350M 34.7→36.6 (+5%), StarCoder-1B 14.0→18.9 (+36%), Phi-1 1.3B 41.4→43.0 (+4%), Qwen2.5-Coder-1.5B 39.3→44.2 (+12%), LLaMA2-7B 26.9→27.4 (+2%), LLaMA3-8B 44.6→45.4 (+2%), Qwen2.5-Coder-14B 42.3→46.0 (+9%). Several per-task differences not significant; LLaMA2 clone detection drops 40.0→39.0; DFG contributed more than AST; LoRA vs full fine-tuning confounds size comparison. — [arXiv v4](https://arxiv.org/html/2409.04183v4)
- CGBridge (KDD '25): frozen Qwen2.5-Coder 1.5B/7B, CodeLlama-7B, DeepSeek-Coder 1.3B/6.7B; graph Transformer encoder over tree-sitter AST+CFG+DFG pretrained with contrastive + edge-type objectives; Q-Former-style bridge produces soft prompts. Translation execution accuracy on Qwen2.5-Coder-7B: CGBridge 98.26% vs LoRA 97.17% vs zero-shot 89.46%; AST-only graph 84.04% EA vs full AST+CFG+DFG 89.11% (1.5B ablation). **Negative:** serialised "GraphText" prompts often underperform zero-shot (Qwen-7B ROUGE-L 15.94 vs 19.91); LoRA beats CGBridge on several lexical metrics (METEOR 20.94 vs 15.73); CGBridge trains 180.8M params vs 18.5M for LoRA; no data-efficiency study. — [arXiv html](https://arxiv.org/html/2512.07666v1)
- IRCoder (Nichols et al. 2025): heterogeneous 2-layer GCN over LLVM-IR graphs (6 node types, 8 edge types; LLVM 16/llvmlite) prepended as soft prompts to a **frozen DeepSeek-Coder-6.7B**; IRCoder best on POJ-104 and DevMap, beats text-only DeepSeek-Coder on ParEval translation (largest gain OpenMP→CUDA); Type and Dataflow edges matter most, CFG removal costs ~4 points on DevMap; slightly worse than GNN-only on Juliet; no numbers in text (figures only), no scale/data-efficiency study. — [arXiv html](https://arxiv.org/html/2507.11467v1)
- GrammarCoder (2025): gains over token-based continued pretraining persist at 1.3B, 1.5B and 7B (HumanEval +19.5/+15.3/+7.9 points) — absolute gap narrows at 7B but the authors do not test larger. — [arXiv html v2](https://arxiv.org/html/2503.05507v2)
- CGM (2025): Qwen2.5-72B with repository code graph integrated into attention (graph-aware attention mask between node tokens, LoRA fine-tuning per search summary) + adapter; SWE-bench Lite 43.00%. No "without graph" ablation seen in the abstract. — [arXiv abs](https://arxiv.org/abs/2505.16901)
- Gong dissertation: SAFIM evaluation of 15 LLMs "challenge[s] the idea that 'big model = good performance'". — [EECS-2025-50](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2025/Archive/EECS-2025-50.pdf)

**Negative / null evidence at LLM scale**
- "Do Code LLMs Do Static Analysis?" (Chia-Yi Su, Collin McMillan; arXiv 2505.12118, May 2025): Jam (350M), CodeLlama-Instruct-13B (QLoRA), GPT-4o mini, Gemini on AST (srcML), call graph (Doxygen), DFG (Joern) generation. Fine-tuned CodeLlama: call-graph pair accuracy 0.94 but chain accuracy 0.22; DFG Jaccard 0.623 with chain accuracy 0.124. Pretraining on static-analysis outputs mostly did **not** improve downstream tasks: summarisation no significant change; generation Java BLEU 31.42→34.22 with DFG pretraining (p<0.001) but other variants no gain; translation C/C++ 37.82→41.64 not significant (p=0.91). Conclusion: static-analysis pretraining does not reliably improve code intelligence tasks. — [arXiv html](https://arxiv.org/html/2505.12118v1)
- "A Critical Study of What Code-LLMs (Do Not) Learn" (Abhinav Anand, Shweta Verma, Krishna Narasimhan, Mira Mezini; arXiv 2406.11930, Jun 2024): CodeBERT, GraphCodeBERT, CodeT5 220M, CodeT5+ 220M/770M/2B, PLBART, UniXcoder, CodeGen 3.7B, CodeRL; tree-sitter AST motifs + GraphCodeBERT-style DFG; attention-map graph comparison (threshold 0.05) and DirectProbe. Models encode ~30–40% of syntactic relations and ~50% of data-flow relations; syntax–identifier edges largely absent (GED per node ×1.5–2); **fine-tuned and larger models (CodeGen 3.7B, CodeT5+ 2B) encode syntax and data flow worse than smaller pretrained models**; encoder-only models encode DFG better than encoder-decoders. — [arXiv html](https://arxiv.org/html/2406.11930v1)
- "Unveiling Code Pre-Trained Models: Investigating Syntax and Semantics Capacities" (Wei Ma, Shangqing Liu, Mengjie Zhao, Xiaofei Xie, Wenhang Wang, Qiang Hu, Jie Zhang, Yang Liu; ACM TOSEM 33(7), 2024; arXiv 2212.10017): probes CodeBERT, GraphCodeBERT, CodeT5, UniXcoder plus StarCoder, CodeLlama, CodeT5+ for AST, CFG, CDG, DDG reconstruction; syntax well captured, semantics uneven; **LLMs do not generally beat the smaller pretrained models by a significant margin**; shallow layers outperform deep ones. — [Crossref record](https://api.crossref.org/works/10.1145%2F3664606); [arXiv](https://arxiv.org/abs/2212.10017v3)
- CoCoNUT (Claas Beger, Saikat Dutta; LLM4Code@ICSE 2025; arXiv 2501.16456): best model (Gemini) correctly generates only 47% of HumanEval execution traces; <5% accuracy on recursion/parallel traces (OOP excepted). — [LLM4Code page](https://conf.researchr.org/details/icse-2025/llm4code-2025-papers/19/CoCoNUT-Structural-Code-Understanding-does-not-fall-out-of-a-tree-Virtual-Talk-)
- "The Shortcomings of Code LLMs in Modeling Code Properties" (Srivishnu Pyda, Daniel Nichols, Abhinav Bhatele; LLM4Code 2025; IEEE Xplore 11028359) and "Understanding Code Properties: Is Code All You Need?" (Mahmoud Jahanshahi, Audris Mockus; LLM4Code 2025) both argue text-only internal representations fail to capture code properties and that structured representations work better for some properties — **abstract/listing level only; experiments not retrieved.** — [Pyda listing](https://dando18.github.io/publication/2025-05-llm-code-shortcomings); [Jahanshahi & Mockus listing](https://conf.researchr.org/details/icse-2025/llm4code-2025-papers/5/Understanding-Code-Properties-Is-Code-All-You-Need-)

**Earlier probing studies (code LMs already encode syntax)**
- Wan et al., "What Do They Capture?" (ICSE 2022, pp. 2377–2388): CodeBERT/GraphCodeBERT attention aligns strongly with syntax; syntax preserved in every layer; syntax trees can be induced; authors suggest incorporating syntax into pretraining may still help. — [arXiv](https://arxiv.org/pdf/2202.06840); [ICSE page](https://conf.researchr.org/details/icse-2022/icse-2022-papers/14/What-Do-They-Capture-A-Structural-Analysis-of-Pre-Trained-Language-Models-for-Sour)
- AST-Probe (José Antonio Hernández López, Martin Weyssow, Jesús Sánchez Cuadrado, Houari Sahraoui; ASE 2022, DOI 10.1145/3551349.3556900): a low-dimensional syntactic subspace exists in CodeBERT, GraphCodeBERT, CodeT5, CodeBERTa, RoBERTa from which the full AST can be recovered; middle layers encode most AST information. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2206.11719); [ASE page](https://www.se.cs.uni-saarland.de/conferences/ASE/ase2022/details/ase-2022/ase-2022-research-papers/12/AST-Probe-Recovering-abstract-syntax-trees-from-hidden-representations-of-pre-traine.html)
- Troshin & Chirkova, "Probing Pretrained Models of Source Codes" (BlackboxNLP 2022, pp. 371–383; arXiv 2202.08975): models encode syntactic structure/correctness, identifiers, data flow, namespaces; may fail on semantic equivalence; study examines effects of pretraining objective, model size, fine-tuning (specific size findings not extracted). — [ACL Anthology](https://preview.aclanthology.org/add_acl24_videos/2022.blackboxnlp-1.31); [arXiv](https://arxiv.org/abs/2202.08975v3)
- DeepCodeProbe (Vahid Majdinasab, Amin Nikanjam, Foutse Khomh; arXiv 2407.08890, 2024): small task-specific models (AST-NN, FuncGNN, SummarizationTF, CodeSumDRL) learn only abstractions of syntax (full-AST probe accuracy 8–42%); adding parameters improves syntax learning "to some extent"; recommends explicit AST/CFG encodings for **small** models. — [arXiv html](https://arxiv.org/html/2407.08890v1)
- Neuron-Guided Interpretation of Code LLMs (Zhe Yin, Xiaodong Gu, Beijun Shen; FSE 2026; arXiv 2512.19980): Llama-3.1-8B and Qwen2.5-Coder-32B; lower layers encode language-specific syntax, middle "concept layers" encode cross-language semantics; no scale comparison. — [arXiv abs](https://arxiv.org/abs/2512.19980)

### Inferences
- The field has not produced a controlled scaling study (same data, same objective, with/without structure, across ≥3 orders of magnitude). GALLa's 350M→14B sweep is the closest and shows no monotone decline, but it confounds LoRA vs full fine-tuning and multi-task training.
- Probing results (syntax largely present even in 125M encoders; semantics/data-flow weakly and non-monotonically encoded with scale) suggest that if structure still helps at scale it is more likely to be data-flow/control-flow (semantic) structure than AST (syntactic) structure — consistent with GALLa (DFG > AST), CGBridge (AST-only 84.0 vs AST+CFG+DFG 89.1 EA), and IRCoder (dataflow/type edges most important).
- Serialising graphs as text into prompts is repeatedly reported as harmful or neutral (CGBridge GraphText; Agarwal's "+Trees without tokenizer" ablation), whereas learned soft tokens or objective-level structure are the routes that show gains.

### Gaps
- No study found that injects AST/DFG into StarCoder2-15B+, CodeLlama-34B/70B, DeepSeek-Coder-33B or Qwen2.5-Coder-32B with a matched no-structure control (CGM uses Qwen2.5-72B but no ablation was visible).
- Troshin & Chirkova's specific model-size findings and the full Pyda / Jahanshahi–Mockus experiments were not retrieved.

## Key Question 3 — Which papers report learning curves vs training-set size or few-shot adaptation with vs without structure?

### Takeaway
Only two code papers in scope report explicit low-resource curves: Agarwal et al. 2024 (structured CSTs; 100–10k examples; large gains, e.g., 100 structured examples ≥ 1.8k plain examples on CoNaLa) and SAT 2024 (auxiliary AST-distance loss; 20–80% data; gains of 0–1.4 points that are small and non-monotone). No 2025–2026 GNN+LLM paper reports data-efficiency curves.

### Cited Findings
- Agarwal et al. 2024, low-data results (CodeT5-S / CodeGen-S = continually pretrained on serialised CSTs): translation — with 100 examples CodeT5-S beats CodeT5 by ≥5 CodeBLEU on CodeXGLUE Java↔C#, CodeGen-S beats CodeGen by ≥10 pp passing programs on TransCoder; CodeT5-S with 3k examples matches CodeT5 with 10.3k. Generation — on CoNaLa CodeT5-S with 100 examples beats CodeT5 with >1.8k; on Concode structured models with 500 examples ≈ base models with 10k. Summarisation — CodeT5 plateaus above 1k examples, CodeT5-S reaches that level with <200; at 1k, +2 BLEU. — [arXiv html](https://arxiv.org/html/2401.10716v1)
- Agarwal et al. 2024, ablation at 500 examples (Java→C# CodeBLEU / CoNaLa CodeBLEU / Go BLEU): CodeT5 76.24/18.86/17.51; +trees without tokenizer change 65.04/3.94/16.03 (**structure as raw text hurts badly**); +tokenizer 77.83/25.99/16.69; full CodeT5-S 81.91/30.58/24.49; MSP-only 81.35/29.53/17.49; MNP-only 74.51/24.18/16.15. — [arXiv html](https://arxiv.org/html/2401.10716v1)
- Agarwal et al. 2024, model-size table at 100 examples (CodeT5-S gain over CodeT5, Java→C# / CoNaLa / Go): 60M +6.19/+6.96/+2.89; 220M +6.07/+9.33/+5.37; 770M +4.97/+7.13/+9.50 — gain does not vanish at 770M; the 770M model is not always better than 220M (attributed to fine-tuning artefacts with limited data). Comparison at 100 examples: CodeT5-S 220M 72.79/23.86/22.93 vs StructCoder 220M 72.10/20.28/11.22, UniXcoder 71.38/12.92/18.02, PLBART 66.28/12.43/12.57. **No full-data regime and no inference-cost measurement reported.** — [arXiv html](https://arxiv.org/html/2401.10716v1)
- SAT 2024, low-resource table (base → +SAT): 20% data CodeBERT Ruby BLEU 11.64→11.98, Java→C# EM 56.10→57.20; CodeT5 Ruby 15.18→15.89, EM 61.10→61.90; 40% CodeBERT EM 59.00→60.40; 80% CodeBERT Ruby 11.87→11.75 (**−0.12**), CodeT5 EM 66.40→66.20 (**−0.20**). Authors claim gains grow as data shrinks; the trend is loose and no significance tests. — [arXiv html](https://arxiv.org/html/2404.07471)
- Code Transformer (ICLR 2021): multilingual Structure+Context training gives the strongest gains on low-resource languages; Context-only multilingual training does not. — [arXiv abs](https://arxiv.org/abs/2103.11318)
- GALLa: no dedicated data-efficiency experiment (626K graph pairs, ~770K GraphQA examples). — [arXiv v4](https://arxiv.org/html/2409.04183v4)
- CGBridge: "No data-efficiency experiments." — [arXiv html](https://arxiv.org/html/2512.07666v1)
- IRCoder: "No data-efficiency or training-set-size experiments are reported." — [arXiv html](https://arxiv.org/html/2507.11467v1)
- K-ASTRO calls itself "few-shot" but reports no few-shot experiments. — [arXiv html](https://arxiv.org/html/2208.08067)
- PRISM: no data-efficiency study. — [arXiv html](https://arxiv.org/html/2609.38601)
- AST-T5: no scaling or data-efficiency study. — [arXiv html](https://arxiv.org/html/2401.03003v1)

### Inferences
- The strongest data-efficiency claim in the literature (Agarwal et al.) rests on structure-as-tokens plus continual pretraining, and the ablation shows the continual-pretraining objectives (MSP) do most of the work; so "data efficiency from structure" is at least partly "data efficiency from an extra structure-aligned pretraining stage", which text-only continual pretraining baselines were not run to control for.
- The GNN-branch papers of 2025–2026 leave data efficiency untested, which is a clear open niche.

### Gaps
- No paper found reports sample-efficiency curves for a GNN/graph-prefix on a frozen decoder LLM.
- Agarwal et al.'s per-size curve values are in figures only; exact numbers at each training-set size were not extractable.

## Key Question 4 — Which papers inject structure into a FROZEN or LoRA-tuned decoder code LLM, and how?

### Takeaway
Four mechanisms are documented: (1) graph-encoder → soft-prompt/prefix tokens with the LLM frozen (CGBridge, IRCoder, CodeGRAG soft token, GALLa stage 1, PRISM's token generator); (2) gated cross-attention from graph tokens into a frozen LLM with LoRA (PRISM); (3) residual fusion of GNN features into intermediate LLM layers (CGFuse); (4) graph-aware attention masks between node tokens with LoRA (CGM). Only GALLa discards the graph at inference; the others pay a context or latency cost.

### Cited Findings
- **CGBridge (KDD '25)** — LLM fully frozen; only the Bridge (L_b-layer Transformer with N_q=32 learnable queries) trained; soft prompt tokens prepended; graph encoder pretrained (InfoNCE + edge-type prediction) and aligned with graph-text contrastive/matching/grounded-generation losses; removing encoder pretraining drops CodeBLEU 69.81→57.20; inference ~4× faster than LoRA (215 ms vs 969 ms on 1.5B) but 180.8M trainable params. — [arXiv html](https://arxiv.org/html/2512.07666v1)
- **GALLa (ACL 2025)** — stage 1 frozen LLM (train GNN + cross-attention adapter on Graph2Code); stage 2 unfreeze LLM (LoRA r=64 for 7B/8B/14B) on Graph2Code + GraphQA (edge/parent/child prediction) + downstream data; GNN/adapter discarded at inference; MLP adapter and MagNet encoder slightly outperformed defaults; single-task fine-tuning with GraphQA caused template leakage and a large drop on C defect detection. — [arXiv v4](https://arxiv.org/html/2409.04183v4)
- **IRCoder (2025)** — frozen DeepSeek-Coder-6.7B; input `[BOS, G, V1…V|V|, T1…T, EOS]` (graph embedding + node embeddings prepended); only the 2-layer heterogeneous GCN trained with next-token loss, 1 epoch; graph tokens consume context (reducing them is future work). — [arXiv html](https://arxiv.org/html/2507.11467v1)
- **CodeGRAG (2024)** — two routes: text "meta-graph" prompt for frozen APIs (GPT-4o-mini HumanEval-X 79.88 vs 78.66 raw code) and a single soft token `<GraphEmb>` from a pretrained GNN over CFG+DFG for tunable models (CodeLlama-7B APPS Python 26.15 SFT → 30.26; Gemma-7B CodeForce C++ 14.76 → 19.13). — [arXiv](https://arxiv.org/abs/2405.02355v4)
- **PRISM (MLCAD '26)** — frozen Llama-3.1-8B-Instruct; three GATv2 streams (AST/CFG/DFG from Python `ast`, C/C++ mapped onto the same vocabulary) → 768-d descriptor → k=128 graph tokens; **gated cross-attention at layer 0** (sigmoid gate, identity when closed) + LoRA r=12 on q/k/v/o; HLS synthesis rate 26.9% vs 7.7% text-only; ~3× slower per query; CHStone 0%; HumanEval tied (98.8 vs 97.6) under clean extraction. — [arXiv html](https://arxiv.org/html/2609.38601)
- **CGFuse (FORGE 2026)** — "infuses learned graph features into the intermediate layers of pre-trained language models" (GNN over AST + DFG, residual fusion per search summary); up to 10–16% BLEU / 6–11% CodeBLEU improvement on code generation (CONCODE per summary); frozen/LoRA status, LLM names and sizes **not visible on the abstract page**. — [arXiv abs](https://arxiv.org/abs/2605.03689); [emergentmind summary](https://www.emergentmind.com/papers/2605.03689)
- **CGM (2025)** — "integrate repository code graph structures into the LLM's attention mechanism" and "map node attributes to the LLM's input space using a specialized adapter"; search summary describes a graph-aware attention mask replacing the causal mask between node tokens and LoRA fine-tuning; Qwen2.5-72B; SWE-bench Lite 43.00%. — [arXiv abs](https://arxiv.org/abs/2505.16901)
- **K-ASTRO v3 (2025)** — frozen OpenAI embeddings + ~1M-parameter single-layer Transformer whose attention map is additively biased (A′ = A + B_max) by log-binned AST node-type co-occurrence matrices from Clang-14 ASTs; concatenated with the LLM embedding into an MLP; CPU throughput 1,441–12,989 samples/s. (Attention-bias injection, but into a tiny side model, not the LLM.) — [arXiv html](https://arxiv.org/html/2208.08067)
- **SAT (2024)** — structure enters only through an auxiliary loss on the first-layer attention matrix during fine-tuning of encoder/encoder-decoder models; no architectural change; not for decoder-only generation from text. — [arXiv html](https://arxiv.org/html/2404.07471)
- **Agarwal et al. 2024** — decoder-only CodeGen-Multi 350M adapted via continual pretraining + fine-tuning on serialised CSTs with added non-terminal tokens (full-parameter, not LoRA). — [arXiv html](https://arxiv.org/html/2401.10716v1)
- Analogous non-code mechanisms found in the same sweep: Graph-KV ("Breaking Sequence via Injecting Structural Biases into LLMs", NeurIPS 2025, arXiv 2506.07334) and "The Gate Always Closes: On Injecting Auxiliary Signals into Frozen Vision-Language Models" (arXiv 2607.23335; reports that graph-derived causal-mask bias into a LoRA-tuned frozen VLM can be suppressed) — **not code-specific, titles only.** — [Graph-KV](https://arxiv.org/abs/2506.07334); [Gate Always Closes](https://arxiv.org/pdf/2607.23335)

### Inferences
- **No paper found injects a GraphCodeBERT-style data-flow attention mask or an attention-score bias directly into the self-attention of a frozen/LoRA-tuned decoder code LLM for general code tasks**; the closest are CGM (repository-graph mask, 72B, SWE-bench) and PRISM (cross-attention, HLS). This is an open design space.
- Soft-prompt approaches trade trainable parameters (CGBridge 180M) or context length (IRCoder, PRISM k=128 tokens) for leaving the LLM intact; GALLa's "train with graphs, infer without" sidesteps inference cost but makes the structure an auxiliary training signal rather than a runtime input.

### Gaps
- CGFuse's fusion layer details, LLM sizes, and frozen/LoRA status need the full text (arXiv html not fetched).
- CGM's graph construction, LoRA configuration and no-graph ablation were not retrieved.

## Key Question 5 — Program-classification / clone datasets with reliable labels (POJ-104, CodeNet, CodeXGLUE clone detection): structure-aware vs plain LMs, with numbers

### Takeaway
On POJ-104 MAP@R the ordering among ~125M–220M pretrained models is UniXcoder 90.52 > CodeT5 88.65 > SynCoBERT 88.24 > PLBART 86.27 > GraphCodeBERT 85.16 > CodeBERT 82.67 (explicit DFG-attention GraphCodeBERT gains +2.5 over CodeBERT but trails AST-serialisation-pretrained UniXcoder, whose own AST ablation costs −1.8); on CodeNet classification a pretrained C-BERT wins on Java250/Python800 (97.4/97.1%) while GIN-V GNNs win on C++1000/C++1400 (96.6/96.4%); from-scratch GNNs reach 92–96% on POJ-104 versus 82–88% for from-scratch sequence models.

### Cited Findings
- POJ-104 MAP@R (UniXcoder Table): UniXcoder 90.52; CodeT5-base 88.65; SynCoBERT 88.24; PLBART 86.27; GraphCodeBERT 85.16; CodeBERT 82.67. BigCloneBench F1: 95.2 / 95.0 / — / 93.6 / 95.0 / 94.1. UniXcoder w/o AST: POJ-104 88.74; w/o comment 87.05. — [UniXcoder ar5iv](https://ar5iv.labs.arxiv.org/html/2203.03850); CodeXGLUE POJ-104 README defines MAP@R with R=499 and lists CodeBERT 82.67 — [CodeXGLUE README](https://github.com/microsoft/CodeXGLUE/blob/main/Code-Code/Clone-detection-POJ-104/README.md)
- GraphCodeBERT BigCloneBench F1 0.950 vs CodeBERT 0.941. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2009.08366)
- AST-T5 CodeXGLUE clone detection F1 98.6 vs CodeT5 97.2 (T5 baseline 96.9; +AST segmentation 98.3). — [arXiv html](https://arxiv.org/html/2401.03003v1)
- GALLa CodeXGLUE clone detection: LLaMA2-7B drops 40.0→39.0 with graph alignment (one of the negative cells); overall averages in KQ2. — [arXiv v4](https://arxiv.org/html/2409.04183v4)
- Project CodeNet (Puri et al., NeurIPS 2021 datasets track): labels = problem ID of the submission (near-duplicates removed, duplicate problems manually checked). Test accuracy (%): Java250 — MLP BoT 71.00, CNN 89.52, **C-BERT 97.40**, GCN 92.70, GIN 93.26, GIN-V 92.77; Python800 — C-BERT 97.09, GIN-V 94.54; C++1000 — C-BERT 93.79, **GIN-V 96.64**; C++1400 — C-BERT 91.83, **GIN-V 96.36**. - Tree-Transformer (arXiv 2208.08643) on POJ: GCN 93.93%, GIN 95.76%, plain Transformer 88.13%, Tree-Transformer 96.12%. — [arXiv](https://arxiv.org/pdf/2208.08643)
- IRCoder: on POJ-104 "IRGraph matches ProGraML, Deepseek-Coder is worse, IRCoder is best" (numbers in figures only). — [arXiv html](https://arxiv.org/html/2507.11467v1)
- GrammarCoder semantic classification (CodeNanoFix F1): 79.30 vs DeepSeek-Coder-1.3B 67.06; 74.36 vs Qwen2.5-1.5B 68.38. — [arXiv html v2](https://arxiv.org/html/2503.05507v2)

### Inferences
- On reliable-label classification, explicit graph structure clearly beats *from-scratch* sequence models (+8–10 points on POJ-104), but once a text-only model is pretrained the gap closes or reverses (C-BERT > GNN on Java/Python CodeNet; UniXcoder > GraphCodeBERT on POJ-104). The remaining GNN advantage on C++1000/1400 and in IRCoder suggests structure still helps on long, algorithmic C/C++ programs where sequence-length limits bite.
- Because POJ-104 and CodeNet have essentially exact labels, they are the best available testbeds for isolating structure effects, in contrast to Devign/BigVul whose label accuracy is 47–80%.

### Gaps
- No 2024–2026 paper was found that reports POJ-104 or CodeNet numbers for a frozen/LoRA decoder LLM with vs without a structure branch in tabular form (IRCoder's are figure-only).
- SynCoBERT's BigCloneBench number and TreeBERT/Code Transformer classification numbers were not located.
